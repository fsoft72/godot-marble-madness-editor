# Marble Madness Godot Port - Design

## Intent

Port the web project `~/dev/games/marble-madness` (Three.js, vanilla JS, ~3200 lines) to Godot.
The source is a 3D level editor for Marble Madness style levels, with one preset level (Level 1).
The owner wants both the editor and a playable game in Godot, starting with the editor.
The source is the reference for behavior and look: `index.html`, `css/style.css`, `js/main.js`,
`js/geometry.js`, `js/textures.js`, `js/level01Preset.js`, `work/data/level01.png`.

## Goals

- A standalone Godot scene containing the full editor, with its own UI built from `Control` nodes.
  It runs inside the exported game, not as an `EditorPlugin`.
- Same level model as the source: grid of 3x3-sub-tile blocks, each with `elevation`, `slope`, `tilt`,
  `rotation`, `shape`, `element`, `elemRotation`, `decal`, `decalRotation`, `isVoid`, and a 4x4 `vGrid`
  of vertex heights relative to elevation.
- JSON import and export compatible with the source format, so levels move between the web and Godot versions.
- Procedural block meshes in Godot (`ArrayMesh` / `SurfaceTool`), ported from `geometry.js`:
  stepped sub-tiles, cliff walls with orange trim, 4-tone Atari shading, guard tubes, elements (tubes, cones, flags).
- Procedural textures in Godot (`Image` / `ImageTexture`), ported from `textures.js`: 3x3 tile base, decals
  (arrows, GOAL, numbers), cliff walls, flag.
- Editor tools: select, block brush, element placement, decal placement, eraser, eyedropper.
  Inspector for the selected block, undo and redo, orthographic isometric and perspective cameras,
  "Arcade View" reset, grid toggle, reference image overlay, Level 1 preset, clear map.
- UI language switch EN / IT.
- Later: a playable marble using Godot physics.

## Non-goals

- Pixel-identical copy of the web UI. Where Godot offers a more natural solution (theme, `Control` layout,
  `Camera3D`, input actions), use it.
- An `EditorPlugin` version.
- Reproducing the original arcade's custom physics.
- New levels, new game modes, or new element types in this port.

## Anti-goals

- A port that looks right but cannot load a JSON level exported by the web editor.
- Marble collision that differs from the visible mesh (the collider must come from the same generated geometry).

## Constraints

- Godot 4.6 (installed at `/home/fabio/bin/godot`), GDScript. These are the assistant's calls, not discussed in depth.
- Project root: `/home/fabio/dev/godot/marble-madness-editor` (empty at the start).
- Owner conventions (global `CLAUDE.md`): code, comments, names in English; constants UPPER_CASE;
  early-exit conditions at the top of functions; comments on every function; keep `CHANGES.md` at the project root.
- No external art assets for the level: all geometry and textures are generated by code, as in the source.

## Decisions made with the owner

- Editor is a standalone in-game scene, not an editor plugin.
- Fidelity: adapt to Godot idioms where they are more natural; keep behavior, data format and overall look.
- Marble physics: Godot `RigidBody3D`, with collision built from the generated block meshes.
- Order of work: editor first, then game.

## Phases

1. **Editor core:** data model and JSON, mesh generation per block, cameras, tools, inspector, undo and redo.
2. **Polish:** i18n EN/IT, reference overlay, Level 1 preset, remaining UI parity.
3. **Game:** playable marble. "Test Marble" inside the editor is the first step, then a game scene that loads level JSON.

## Left to the builder

- Scene and script structure, naming, autoloads, how to split `geometry.js` into GDScript modules.
- How to render the 4-tone shading (vertex colors vs shader).
- Block picking method (raycast vs grid math).
- Undo/redo mechanism (command stack vs snapshots).
- Marble collision shape details and tuning of mass, damping and steering force.
- Test approach for the port (for example a headless script that builds Level 1 and checks mesh and JSON round trip).

## Assistant's calls (not discussed with the owner, please check)

- **Platform:** Linux/Windows/macOS desktop. JSON import and export use native `FileDialog`. Superseded for the player: the owner asked for a standalone web build without the editor (see `CHANGES.md`).
- **JSON compatibility:** the loader is tolerant (missing fields get the defaults used by the source `setBlock`, unknown keys are ignored).
  Round trip must be semantic, not byte-identical. The web format is defined by the source code; the builder derives it from `js/main.js`.
- **Grid size:** square, fixed per level, read from the JSON. The source `state` says 13x13 and the Level 1 preset says 14x14, so the default for a new map is the preset's 14x14.
  "Clear" empties the map and keeps the current size. No resize UI in this port.
- **Reference overlay:** `work/data/level01.png` is copied into the project as a tracing aid. "No external assets" means no art, models or textures for the level itself.
- **Performance:** rebuild only the meshes of blocks that changed (per-block cache), not the whole level.
  Collision is built per block from the same generated mesh.
- **Phase 3 scope:** not planned in detail here. It gets its own design after phases 1 and 2 are done.
  Optional extra JSON fields (for example start and goal positions) are allowed there; the web editor ignores them.
- **Strings:** all UI strings live in one translation table, instead of the mix of labels and i18n keys in the web UI.
